# Can a standalone `duo` binary replace apps? — measured 2026-08-09

**Yes.** A Developer ID-signed standalone executable holds its own App Management
grant on macOS 27.0 (build 26A5388g), and with it can replace a third-party app
in `/Applications` with no app bundle, no helper, and no Full Disk Access.

This settles the scope of `duo install`: the in-place swap routes (Sparkle,
Vendor, GitHub) are available to the CLI, not just Homebrew and `.pkg`. The
fallback ladder — shipping the CLI inside `DuoUpdater.app`, or proxying the apply
phase to the running app over XPC — is not needed.

Re-run it with the `duo-tcc-spike` target in `App/project.yml` (not shipped;
`swift build` will not do, its ad-hoc signature cannot hold a grant).

## What was measured

A reversible write of `Contents/.duo-tcc-probe` into `/Applications/VLC.app`,
which is signed by team `75GAHG3SZQ` — a third party. That matters: a bundle we
create ourselves is not "managed" in TCC's eyes and writes fine regardless, and
apps signed by our own team are exempt. Either would have reported a pass that
meant nothing. VLC's signature was verified intact afterwards.

| launched from | before the grant | after the grant |
|---|---|---|
| a shell | `granted` · write **ok** | `granted` · write **ok** |
| a shell, disclaiming responsibility | `notDetermined` · **EPERM** | `granted` · write **ok** |
| launchd (`ppid 1`, no terminal anywhere) | `notDetermined` · **EPERM** | `granted` · write **ok** |

## Three things that were not obvious

**The first `granted` was borrowed, not held.** macOS attributes TCC to the
*responsible* process, and a program started from a terminal is normally the
terminal's responsibility. The binary reported `granted` before it had any grant
at all, because the caller had one. Only disclaiming responsibility — or being
started by launchd, which has the same effect — exposed that it had nothing of
its own. A spike that only tested the shell path would have concluded "it works"
and been wrong about why.

**`responsibility_spawnattrs_setdisclaim` should be the CLI's default, and it is
not the "fix" the plan assumed.** The plan expected disclaiming to turn "fails
from Terminal" into "works everywhere". It does the opposite: it *removes* the
borrowed grant. What it buys is determinism — with it, `duo` always uses its own
grant, so it behaves identically whether it was started from Terminal, from a
script, from launchd, or from CI. Without it, `duo` inherits whatever the caller
happens to have, which means it can fail on a machine where `duo` is granted but
the terminal is not, and silently succeed on one where the terminal is granted
and `duo` is not.

The SPI exists and works on macOS 27. Its signature is
`int responsibility_spawnattrs_setdisclaim(posix_spawnattr_t *, int)` — a pointer
*to* the attribute. Passing the attribute by value compiles cleanly and returns
non-zero, which reads as "the SPI refused" rather than "we called it wrong".

**Full Disk Access is not required.** In the granted launchd run, FDA still read
`denied` while the swap succeeded. App Management alone is sufficient, which is
the narrower permission and the one to ask for.

## What this obliges `scripts/build-cli.sh` to do

The grant is bound to the binary's designated requirement **and its path**. So:

- Sign with `Developer ID Application`, team `RS59HDH7Y3`, and verify the
  designated requirement is identity-based (`anchor apple generic and identifier
  …`) rather than a bare cdhash — `scripts/install.sh` already has this gate and
  it should be reused verbatim, not reimplemented.
- Install to a fixed path and never move it. A rebuild to a different location
  starts over with `notDetermined`.
- `/usr/local/libexec` needs an admin password; `~/.local/libexec` is equally
  stable and needs none. The spike used the latter.
