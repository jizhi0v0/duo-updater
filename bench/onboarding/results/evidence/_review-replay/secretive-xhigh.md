**Blocking findings: 1**

1. `DuoUpdaterCore/Sources/DuoUpdaterCore/Recipes/com-maxgoedjen-Secretive-Host.swift:18`: the new stable one-click rule reaches Secretive nightly copies. They are detected as `.stable`, shown 4.0.0 as an update, and can be one-click "updated" from a newer nightly to an older stable build. The audit records this as a gap, but the reason it gives does not hold.
   - Trigger: a nightly built by the vendor's `nightly.yml` and installed as `Secretive.app` with `CFBundleShortVersionString` = `0.0.0_nightly-2026-10-13`. `ReleaseChannel.detect` finds no channel signal. The bundle ID, display name and filename are the stable ones, and the version-tail rule only accepts a `-` before the word. So the copy is `.stable`. The channel gate (`GitHubReleasesSource.swift:640`, `candidates.first(where: { $0.channel == app.releaseChannel })`) then hands it this rule. `/releases/latest` answers v4.0.0, and `VersionComparator` ranks `4.0.0` above `0.0.0_…` because the first token is 4 vs 0. The row offers 4.0.0 with an install button. The vendor signs and notarizes nightlies with the same secrets as releases (`nightly.yml`, "Setup Signing"/"Notarize"), so the Team-ID gate would not stop the swap.
   - Evidence:
     - The detector needs a dash: `ReleaseChannel.swift:407` `#"[0-9]+(\.[0-9]+)+(-[0-9]+)*-"# + word + #"(-[0-9]+)*"#`.
     - The vendor stamps an underscore: `nightly.yml` on `main` runs `sed -i '' -e "s/GITHUB_CI_VERSION/0.0.0_nightly-$DATE/g" Sources/Config/Config.xcconfig`, and `Sources/Secretive/Info.plist` sets `<key>CFBundleShortVersionString</key> <string>$(CI_VERSION)</string>`. Both were fetched through the GitHub API.
     - The repository treats this outcome as a defect. `GitHubReleaseRule.channel`'s doc says "a stable rule can never be served to a nightly install that shares the bundle id". `ChannelGuardTests.swift:250` `dbBrowserStableRecipeDoesNotReachTheNightly` exists for exactly this hazard ("stable is covered by a real registry rule that carries a one-click install spec, and without the channel the nightly install sits squarely in that rule's reach"). `REVIEW.md` names this exact Secretive string as the example.
     - The audit records the gap with reasons that don't hold:
       - `docs/app-audits/com-maxgoedjen-Secretive-Host.md:96` says "暂不为它改全局的渠道检测". The fix isn't global, though. `detect()` already carries bundle-ID-scoped rules for this situation: step 0.6 for the DB Browser nightly, and step 0.7 for Little Snitch, `bundleID == "at.obdev.littlesnitch", … hasStandaloneWord("nightly", in: version)` at `ReleaseChannel.swift:201-206`. That check would match `0.0.0_nightly-…`, since `_` is a word boundary there.
       - `CHANNEL_COVERAGE_TODO.md:278` says "尚未取得真实 nightly 包确认版本串，故未改 `detect()`". But the string is fixed by the vendor source quoted above and by the vendor's own `SemVer.swift` ("Nightlies have the format 0.0.0_nightly-2025-09-03"). The DB Browser scoped rule was itself added from a cask artifact name, not a mounted nightly.
     - The audit doesn't explain why the existing scoped-rule mechanism can't be applied, so by `REVIEW.md` this group counts as neither covered nor recorded.
     - For context: the vendor's own updater also lists 4.0.0 for a `0.0.0` build. Its `UpdateView` then adds a "Download latest nightly" button pointing at `nightly.yml`, and it only opens a page; it never replaces the bundle.
