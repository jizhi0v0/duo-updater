# Recipe data format: why recipes stay Swift

Explains `DuoUpdaterCore/Sources/DuoUpdaterCore/Sources/RecipeCoding.swift` — why
the recipe types have a JSON convention while nothing ships recipes as JSON — and
keeps the evaluation behind that decision, so it can be picked up again without
redoing it.

Every number below is a **one-time measurement taken 2026-09-15** (macOS, Swift
6.4, SwiftPM debug builds), not a tracked metric. Each says who measured it.
"Reported" means taken from the implementing agent's report and not re-run.

## §1 The decision (2026-09-15)

The recipe refactor had three steps:

1. One Swift file per app family under `Recipes/` (PR #606).
2. Recipe comment history moved into `docs/app-audits/<slug>.md` (#607 … #636).
3. Recipe data out of Swift, into data files.

Step 3 was planned as S0 → S1 → S2, with a go/no-go on bulk conversion after S2.
The outcome: **recipes stay Swift. No bulk conversion, no runtime loader, no
generated Swift.**

- **Kept on main:**
  - S0 (#648): the `Codable` convention in `RecipeCoding.swift`.
  - S1 (#651): per-family goldens in `RecipeGoldenTests`. They pin all recipe
    data as a reviewable diff, whatever the format.
- **Removed:** S1's `.json5` digesting in `SourceStamp`, which had nothing left
  to read.
- **Not merged:** S2 (#654), the JSON5 runtime loader piloted on 1Password.
  Closed; the branch `recipes/3-s2-json5-loader` (head `b6ebea69`) is kept as
  the record.

## §2 Options that were evaluated

| | What it is | Verdict |
|---|---|---|
| **A** | Stay Swift, stop after S1 | **Chosen** |
| **A′** | Swift, but recipes in their own SwiftPM target | Only if the edit loop starts to hurt (§5) |
| **B** | Bundled JSON5 decoded at runtime (#654) | Rejected: see §4 |
| **C1** | JSON5/YAML source → generated Swift, committed + drift gate | Rejected: two representations of the same data, no edit-loop gain |
| **C2** | Same, generated by a SwiftPM build-tool plugin | Rejected: no edit-loop gain; xcodebuild plugin validation risk |
| **D** | Build-time compiler → canonical binary artifact → runtime loader | Rejected: everything B costs, plus a format |
| **E** | One signed recipe package for bundled and remote recipes | Rejected: bundled records hold fields that must never come from a server, so one format carries two trust levels |
| **F** | Swift now; a separate remote *patch* format only if remote is built | The remote path, if it ever happens (§6) |

## §3 Measurements

**Edit one recipe → rebuild → run `RecipeGoldenTests`**: measured by the evaluation
on scratch copies of `DuoUpdaterCore`, method copied from S2 (one comment-line
edit, reverted between rounds):

| Layout | edit → `swift build` | edit → golden test |
|---|---|---|
| Swift in Core (today) | 4.27, 3.82 s | 5.91, 4.44 s |
| No-op rebuild (floor) | 1.20 s | 1.92 s |
| 225 families in a separate target (A′) | 2.60, 2.29 s | 4.16, 2.97 s |
| C1 generated Swift in Core | — | 4.43, 4.51 s comment edit; 6.92, 6.97 s data edit |
| C2 build plugin in Core | 4.25, 3.90 s | 4.46, 5.16 s comment edit; 6.89, 6.72 s data edit |

- The generator itself took 0.035 s for 5 families.
- Reported by S2: JSON5 edit → golden test 1.6 s versus 4.3 s for Swift. That is
  close to the no-op floor above, which S2 did not measure.
- **Conclusion:** the cost is compilation, not the file format. The only saving
  available comes from a module boundary, and Swift source can have that too (A′).

**Other numbers:**

- **Regex escaping (step-3 design measurement):** of 728 regexes, 583 contain
  backslashes and 16 need `\\\\` in JSON. There are 778 raw-string literals
  (`#"…"#`) under `Recipes/`, re-counted at close-out.
- **Families that need Swift helper code** (factories or shared constants that
  fill one value in several places): the design count was 12; the evaluation
  named 7 (`com-lemon-lvoverseas`, `com-windscribe-client`,
  `dev-kdrag0n-MacVirt`, `ai-perplexity-comet`,
  `pro-betterdisplay-BetterDisplay`, +2). The discrepancy was not resolved.
- **Runtime decode cost (reported by S2):** 0.4 ms for the index today;
  a synthetic 780 KB directory about 24 ms.
- **C2 feasibility:**
  - Verified under `swift build`: the plugin ran with no prompt, and a JSON
    syntax error failed the build with line and column.
  - **Unverified under `xcodebuild`**: `-skipPackagePluginValidation` exists,
    but whether validation fires for a local-path package plugin was not
    tested. `App/project.yml` consumes `DuoUpdaterCore` by local path. If
    validation does apply, the flag must reach `app-tests.sh`, `build-cli.sh`,
    `install.sh`, `notarize.sh`, `row-state-gallery.sh`,
    `check_localizable_keys.py`, and so to `ci.yml` (through `make test`) and
    `release-build.yml` (through `notarize.sh`).
  - Sources: [SE-0303](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0303-swiftpm-extensible-build-tools.md),
    [Apple forums 820567](https://developer.apple.com/forums/thread/820567).

## §4 Why not JSON5 (or codegen from it)

- **No edit-loop gain** (§3). That was the only measured benefit left once
  step 2 had moved the comments, which were about 70% of recipe bytes (step-3
  design measurement).
- **Authoring gets worse.** Backslashes must be doubled in 583 regexes, there is
  no string concatenation, and the helper-code families stay Swift anyway, so
  authors would face two formats.
- **A second parser is unavoidable.** Foundation's `JSONDecoder` (including
  `allowsJSON5`) silently keeps the FIRST value of a key written twice. A JSON5
  `//` comment also ends at `\r` for Foundation but not for a line-based reader,
  which can hide that duplicate. Canonically equivalent keys (U+212A KELVIN SIGN
  versus `K`) collapse in a Swift dictionary. S2 needed
  `check_recipe_json5.py` to refuse all three.
- **Runtime loading of bundled data only (B, D):** the CLI's data sits outside
  its signature. `duo` is Developer-ID signed and keeps TCC grants, while the
  resource bundle beside it is user-writable. S2 needed a recipe digest embedded
  in the binary, a build-time self-test, and four review rounds (§7). The app is
  unaffected: its resources are sealed by the app signature (verified by
  tampering).
- **Codegen (C1/C2):** removes the runtime and signing costs, but keeps the
  authoring and parser costs. It adds a generator plus either committed
  generated files (two copies of the same data and a drift check) or a build
  plugin.

## §5 When to reopen

| Trigger | Then |
|---|---|
| Remote recipe updates are decided (a server exists), or the 2026-11 check finds the median recipe `fix:`-to-release time over 48 h | Build F (§6). Not D or E. |
| Recipe edits are frequent enough that the rebuild time hurts | A′: move the Swift recipes into their own target. Still Swift. |
| Something other than the app must read recipes (a web catalog, a second client), or recipes are written by people who don't write Swift | C1: data files become the source of truth and Swift is generated, with a drift gate. |

## §6 If remote updates are ever built

The constraints below are carried over from the 2026-08-19 remote-hosting
assessment (quoted, not re-derived here), with field counts added by the
2026-09-15 evaluation, which counted them from the stored properties (not
re-counted).

- **Ship patches, not records.** A patch is a recipe id plus a restricted set of
  fields, merged over the built-in record. `RecipeCoding` decodes whole records,
  and an absent key takes the initializer's default, so an S0-decoded record
  would reset every field the patch did not name. The S0 value shapes (enum
  tags, URLs, proofs) are reusable.
- **Remotable fields:** 43 of 71 record fields across `VendorProbeRecipe` (27),
  `ChangelogRecipe` (27), `GitHubReleaseRule` (12) and `MacAppStoreProbeCase`
  (5). They are the patterns, flags and selection knobs a `fix:` commit touches.
- **Never remotable:**
  - `identities` (`ProbeIdentity` is a file-read primitive), request headers,
    request bodies and `httpMethod`;
  - all of `VendorInstallSpec` / `install`, `installAssetPattern`,
    `installerKind`, and the App Store route fields;
  - all channel-proof tables and Sparkle feed maps (they choose channel and
    installer);
  - adding a new bundle id.
- **URL fields** (`url`, `downloadURL`, `source`, `sourceTemplate`,
  `owner`/`repo`, changelog pages): only with the host pinned to the built-in
  one. A remote URL combined with compiled-in identities would be an
  exfiltration path.
- **Trust:**
  - an Ed25519 signature (reuse `SignatureVerifier.verifyEdSignature`; the
    private key never lives in the hosting repo), a monotonic version and an
    expiry time;
  - the compiled-in recipes are the floor, and any failure falls back to them;
  - discard the whole overlay if it makes more than 20% of entries worse.
- **Format:** strict JSON generated by a script from the Swift diff, not
  hand-written JSON5. Keep the duplicate-key and NFC refusals anyway (§4).
- **Already true:** `SignatureVerifier.verifyTeamIdentifierMatch` anchors an
  install to the Team ID of the app on disk, so a hostile patch cannot swap
  vendors. What remains is downgrade and silent suppression.

## §7 What S2 (#654) learned that outlives it

- **Reading trusted data from the CLI's own signature:** read the embedded
  Info.plist straight from the main image with
  `dlsym(RTLD_MAIN_ONLY, MH_EXECUTE_SYM)` + `getsectiondata("__TEXT", "__info_plist")`
  (`RecipeFamilyFile.embeddedDigest` on the branch). **Not `Bundle.main`**:
  - for a bare executable, CF treats its directory as the bundle, and an
    `Info.plist` placed beside `~/.local/libexec/duo` replaced the embedded one;
  - with a tampered recipe it ran and passed (reproduced on the installed binary
    2026-09-15);
  - `CFProcessPath` (case-sensitive) is honoured by the hardened `duo` and moves
    both the build-stamp and resource-bundle lookups (measured).

  A future remote patch's pinned public key would need the same technique.
- **Crash proof in the build:** `build-cli.sh`'s self-test ran a tampered staged
  copy and required the refusal. That caught "stops reading the digest", which no
  unit test could, because test processes carry no such section. Each run leaves
  one crash report.
- **Packaging:**
  - a SwiftPM `.copy` resource bundle is required beside a copied CLI binary
    (without it: exit 133);
  - SwiftPM did not copy `.DS_Store` into the bundle but did copy other dotfiles
    (reported);
  - Xcode's incremental builds picked up an edited, added and deleted `.json5`
    correctly (measured with `make cli`).
- **JSON5 checker hardening** (`check_recipe_json5.py` on the branch):
  - a comment line is exactly `^[ \t]*//`;
  - refuse `\r`, other control characters, U+2028/2029 and U+FEFF;
  - refuse NUL and lone surrogates in decoded strings (Foundation refuses them;
    Python accepts them);
  - refuse duplicates after NFC.
